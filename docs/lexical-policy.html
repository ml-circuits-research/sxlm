Lexical policy and Unicode mechanisms

The chart recognizer receives three explicit pure SOP entrypoints: lexical prepare, tokenize and terminal. Preparation accepts {with: grammar} and returns an immutable lexical index and classes. Tokenization accepts {text} and returns token records. Terminal matching accepts {symbol, token, knowledge} and returns an array of semantic values. The standalone Grammar constructor requires these entrypoints through its policy option; it has no native terminal fallback. SymbolicModel binds the corresponding pack entrypoints and includes preparation work in installation metrics.

Seventeen authored SOP policies implement index construction, literal and lexical lookup, class selection, category exclusion, case sensitivity and surface preservation. The index is reconstructed by circuits from circuit-produced grammar knowledge. Its keys encode category and normalized spelling without delimiter collisions. Ambiguous lexical values preserve insertion order, record property order and signed zero. This preparation is not a new side table of authored answers.

learned.lexical.normalize is separately synthesized from eight typed examples in training/lexical-normalization.sop, using a teacher-supplied library and candidate operation names. The selected two-operation program composes compatibility normalization with lower casing. Examples distinguish this ordering from lower casing followed by normalization. Both the library choice and examples are author supervision; synthesis is not unsupervised language discovery. The same induced procedure processes literal terminals, lexicon surfaces and parser token values. build:lexical reproduces its source and runtime-bound receipt. The bootstrap stores its evidence under training.components.lexicalNormalization.

The host's new operations are string normalization with an explicit Unicode form, case conversion with an explicit operation, and restricted character-class membership. They contain no words, answer templates or grammar-category names. Membership accepts concatenated character classes with at most one variable repetition; arbitrary regular-expression programs are rejected. It checks the entire string, including any trailing newline. Unicode/ICU versions are already part of runtime identity. These are scoped computational contracts, not a certification of all Unicode implementations or the full native closure.

Grammar.tokenize(text, options) executes the installed token policy and validates its returned evidence. Recognition and construction induction use that same method. The parser validates token text against exact, ordered, non-overlapping half-open UTF-16 source spans. Pure terminal results can be memoized within one parse by the complete symbol and token values, including property order and offsets. Each memo hit charges terminalCacheHits; disabling caching executes the policy again. Grammar knowledge and selected programs are immutable for that parser. Semantic and lexical circuit calls share the outer execution trace and resource budget, so formerly hidden work is inspectable.

The existing 19-node proof regression consumes approximately 91,734 VM nodes with caching and 92,800 without, versus roughly 25,000 before terminal policy migration. This motivated a general default budget of 100,000 nodes. Explicit tighter limits stop computation without committing; the 3,000-node proof limit remains. This is additional visible computation, not an improved asymptotic algorithm or language-quality gain. Structured CLI results also contain fuller traces; consumers must allow for their size.

test/lexical.test.mjs checks primitive errors/budgets, 3,905 character-membership comparisons against independently written finite predicates, historical lexical/parser agreement, classes, exclusion, Unicode values, invalid source spans, explicit callback contracts, and learning ablation/restoration. Sixteen held-out literal normalization pairs include compatibility symbols, combining forms and contextual casing. They are evaluator-owned and excluded from the learner's packet, but share the project author; they are not external blind data. Altering the induced module or removing its evidence invalidates derivation credit.

Native token boundaries remain: the tokenizer groups Unicode letters/numbers and certain internal connectors. Summary word extraction calls the native path, including its normalization convention. Segmentation and completion call lexical.tokenize, whose values use the learned normalization circuit. The SOP parser overwrites token values through the learned normalization circuit, but has not learned token boundaries. Earley agenda scheduling and semantic-alternative enumeration also remain native. These gaps stay visible in the vision audit; no claim is made that all lexical policy or the complete model is learned.

Failure realization receives a small status envelope. The potentially large execution trace is attached to the returned diagnostic result afterwards, preserving observability without consuming the failure renderer's budget on irrelevant input hashing. A regression exercises resource failure after more than 20,000 traced nodes.

Document terminology

The offline phrase compiler accepts named terms and constant category meanings. It shares token prefixes and groups terminal leaves into lexical categories, then emits ordinary grammar providers and SOP projection actions. A document author can therefore supply multiword terms without adding a separate top-level production and semantic action for every spelling. The model still executes the installed lexical and recognition policies. This representation reduces measured chart work for the 320-term fixture in test/phrase-knowledge.test.mjs; it does not establish unrestricted document capacity. Differential checks retain ambiguity, shorter-prefix meanings, normalization and exact nested values, while a separate composition combines two supplied terms in a new structure. The elementary extension also accepts a lexical relation noun once and composes it in assertions, relative restrictions, conditional rules and both directions of selection. For example, mentor in the relational-noun category supplies the same predicate as the existing verb. A supplied custodian meaning transfers to a universal rule and a selection question without editing the host or adding another sentence pattern. These checks establish the scope of the construction; they do not establish unrestricted noun-phrase interpretation or automatic morphology.

Coherent category questions

A declared category connects singular and plural descriptions to classification through the same relation. With the elementary knowledge, What is a cat?, What are cats? and Tell me about cats. return the supported classification chain. Is a cat an animal? checks category inclusion. Is some cat an animal? asks for an instance and remains unknown until the context supplies one. These meanings are selected by declared noun categories and determiners, with no answer-dependent interpretation choice.

The concept compiler accepts category identities, actual singular/plural forms and source-attributed inclusions or explicit disjointness. Multiword terms use the phrase compiler. Each concept declaration supplies reusable instance rules and lexical meanings; it does not supply question/answer pairs. The model can compose those meanings with existing relative restrictions and rule bindings. Classification descriptions verbalize supporting proof statements. They do not supply features absent from the source or explain biological causes.

Composing a learned predicate

The optional construction pack learns the predicate “owned by Mira” in the existing Comp category. Existing grammar then uses it in statements, questions, explicit negation, explanations and supported rule contexts. Teaching it at that shared category makes “Is Pico owned by Mira?” use the same learned argument mapping as “Pico is owned by Mira.” The participle meanings remain supplied lexical knowledge; the composition procedure is learned from annotated phrases under the contract in Training.
